# パイプラインの実装メモ

SPEC本体（[SPEC.md](SPEC.md)）に書かれていない、実装して初めて分かったことの記録。
判断が必要な論点は「★要判断」を付けてある。

---

## 1. ★要判断 テキスト抽出が効かないページは7枚か14枚か

SPEC §0.3 は、テキスト層がほぼ空のページを7枚（PDF 21・24・25・28・29・58・59）としている。
SPEC §3 Phase 1 の規則は「抽出文字数が100字未満のページには `text_extractable: false` を自動で立てる」。

実装して照合したところ、**SPEC §0.3 の表の「抽出文字数」はバイト数だった。**
日本語1文字はUTF-8で3バイトなので、文字数で数え直すと値が変わる。

| PDFページ | SPEC §0.3 の値（＝バイト数） | 文字数 |
|---|---|---|
| 21 | 2 | 2 |
| 24 | 65 | 23 |
| 25 | 44 | 16 |
| 28 | 29 | 11 |
| 29 | 23 | 9 |
| 58 | 20 | 8 |
| 59 | 38 | 14 |

閾値100を**文字数**に適用すると、対象が7枚から14枚に増える。増える7枚は次のとおり。

| PDFページ | 印刷番号 | タイトル | 文字数 |
|---|---|---|---|
| 8 | 7 | 平均寿命と健康寿命の推移 | 85 |
| 13 | 12 | 年齢階級別1人当たり年間外来受診回数 | 81 |
| 14 | 13 | 受診率の推移 | 51 |
| 16 | 15 | がん患者の5年生存率 | 99 |
| 54 | 53 | 消費者物価指数の長期トレンド | 95 |
| 55 | 54 | 賃金の長期トレンド | 83 |
| 63 | 62 | 協会けんぽと健康保険組合の平均総報酬額の推移 | 154バイト / 54文字 |

この7枚は、テキスト層に**タイトルと一文のリード、出典しかなく、グラフの数値は画像の中にある**。
たとえばPDF14ページ（受診率の推移）のテキスト層は全部で次の3行しかない。

```
受診率の推移
高齢者の受診率は、入院について低下傾向にある。
出典：厚生労働省 医療保険に関する基礎資料
```

つまり「グラフの数値を抽出テキストと突合できない」という意味では、
この7枚もSPEC §0.3の7枚と同じ性質を持つ。
一方、§0.3の7枚が「大型の数表が丸ごと画像」であるのに対し、こちらは
「折れ線グラフの目盛りが読めない」という違いがある。数値の密度が違う。

**実装では判断を保留した。**
`_meta.yaml` の `text_ok` を正とし、`build/extract.py` は次の3つを `work/.../pages.json` に記録する。

- `declared_text_ok` — `_meta.yaml` の宣言（これが `text_extractable` になる）
- `auto_by_chars` — 文字数100字基準の自動判定
- `auto_by_bytes` — バイト数100基準の自動判定（SPEC §0.3 を再現する）

食い違うページは `extract.py` の実行時に警告として出る。

判断すべきこと: **上記7枚を `text_ok: false` に倒すかどうか。**
倒す場合、SPEC §6 の品質ルール3により、この7枚も人による数値照合が必須になる（v0.5の対象が14枚になる）。

## 2. 強調表示は機械的に取れる

SPEC §2.1 は「スライド上の強調表示（太字・下線・赤枠）は、事務局がどこを読ませたいかの
直接の証拠なので必ず拾う」としている。目視では見落とすので、`pdftohtml -xml` が出力する
`<b>` タグから機械的に取り出すようにした。

- `build/extract.py` が全ページ分を `work/.../pNNN.bold.txt` に書き出す
- `build/inspect.py --emphasis` で1ページ分を座標付きで確認できる

実際に効いた例。PDF76ページ（医療保険制度改革の経過について）の太字は25スパンあるが、
**高額療養費に関する記述と令和8年度欄には1か所も太字がない。**
目視では気づきにくく、かつ解説の §6 で使える観察になった。

PDF77ページ（患者一部負担の推移）は**太字が1か所もない**（タイトルすら）。
同じ章の隣のページが8か所を強調しているのと対照的で、これも機械的に確認できた事実である。

## 3. 表のセル結合は罫線を検出しないと分からない

`pdftotext -layout` はセルの結合を教えてくれない。
PDF77ページのように「同じ列に並んでいても制度区分ごとに時期の区切りが違う」表では、
結合を読み違えるとある時期の負担割合を隣の時期のものとして転記してしまう。

`build/inspect.py --grid` は、ページを100dpiのグレースケールに描画し、
縦方向に連続する暗画素の列＝罫線を検出する。横罫で区切られた帯ごとに縦罫を出すので、
「この帯には境界の罫線がない＝セルが結合している」が読める。

PDF77ページでの実行結果:

```
横罫（x 271〜704 を貫くもの）: y = [90, 134, 186, 426, 622]
  y   90〜 134: x = [12, 97, 240, 347, 456, 564, 627, 682, 759, 924, 1071]   ← 時期ヘッダ（10列）
  y  134〜 186: x = [12, 97, 112, 240, 759, 782, 1071]                        ← 制度名の行
  y  186〜 426: x = [12, 32, 97, 112, 240, 347, 456, 564, 682, 759, 782, 1071] ← 高齢者（627がない＝結合）
  y  426〜 622: x = [12, 32, 97, 112, 159, 347, 608, 682, 759, 782, 1071]      ← 若人（区切りが違う）
```

`--band` でy範囲を指定すれば、さらに細かい行だけを調べられる。
75歳以上の行と70〜74歳の行で、平成20年4月と令和4年10月の間の罫線の有無が違うことも、これで確認した。

## 4. 数値突合の除外パターン

`build/validate.py` は解説中の数値を原典の抽出テキストと突き合わせるが、
そのまま比較すると転記由来でない数値まで拾ってしまう。次を除外している。

- URL、Markdownリンク、インラインコード
- 「PDF76ページ」「p077」のようなページ参照、「§4-3」の節番号
- ISO形式の日付（`2026-06-05`、`1973-01`）、「第215回」の回次
- **丸囲み数字 ①②…** — NFKC正規化で `1` `2` になるため、`2①②` が `212` という数値に化けていた

残った警告は基本的に妥当なもので、放置してよい。たとえば

- `10.2`（PDF75ページ） — 39.1 − 28.9 を自分で計算した値。SPEC §6 の品質ルール1に従い本文に式を併記してある
- `1984` — 昭和59年を西暦に直したもの
- 他ページの内容を引いた数値（`▲100億円` など）

**計算した数値が警告に出るのは正しい動作である。** 消さないこと。

## 5. `evidence_slides` の逆生成

SPEC §2.3 のとおり、`kb/topics.yaml` の `evidence_slides` は `build/build.py` が
スライド側の `supports_topics` から逆生成する。
`validate.py` は、YAMLに手書きされていたらエラーにする（二重管理の防止）。

逆引きの元になるのは**解説を書いていないスライドも含む**。
`_meta.yaml` の索引に `supports_topics` が入っているためで、
「まだ解説はないが、この論点の材料になるスライド」も論点ビューに出る。

用語の登場スライドも同じ仕組みで逆生成している（`aliases` も拾う）。

## 6. 第三者図版の扱い

`third_party_figure: true` のスライドは、既定では**画像そのものを `dist/` に置かない**。
ビューア側で非表示にするのではなく、配信物に入れない。

`build/build.py --include-third-party` を付けると配信する。
方針を変えるときに触るのはこのフラグ1か所（SPEC §7.2）。

対象は4枚（PDF 16・21・54・55）で、ビルド時に次のように出る。

```
画像      158ファイル（第三者図版 4枚は配信しない）
```

- `dist/` の大きさ: 9.6MB（うち画像が大半）。解説が72枚そろっても画像枚数は変わらない
- コミット対象の大きさ: 解説5枚＋KBで約120KB。SPEC §1.3 の見積り（1セット0.5MB）の範囲内
